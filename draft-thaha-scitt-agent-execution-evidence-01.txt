 Agent Execution Evidence: A SCITT Profile for Verifiable Records of AI
                               Agent Runs
             draft-thaha-scitt-agent-execution-evidence-01

Abstract

   AI agents act through calls to models, tools and other agents.
   Identity work establishes who an agent is and what it may do, but
   leaves execution-evidence formats and assurance criteria out of
   scope.  This document profiles the Supply Chain Integrity,
   Transparency, and Trust (SCITT) architecture for Signed Statements
   that bind an agent's registered identity, declared capabilities,
   risk-based assessment and supervised operational status to a hash-
   chained record of every call the agent makes.  It also defines
   admission records produced where a call is received, and the linking
   of records for requests that pass between agents of different
   operators.  It specifies Registration Policy, offline verification
   and Bundle requirements.  It does not define an accreditation scheme,
   a universal risk classification, an identifier scheme or a policy
   language.

1.  Introduction

   An AI agent is a workload whose behaviour is driven, in whole or in
   part, by a non-deterministic decision process, typically a large
   language model (LLM), and which acts on the world by invoking tools,
   services and resources.  Every consequential thing an agent does
   passes through one of two doors: a call to a model (an inference) or
   a call to a tool.  If evidence is produced at those two doors, bound
   to the agent's identity and to the policy in force, and registered in
   an append-only, non-equivocating log, a third party can later
   establish what the agent did, under which rules, and with which
   configuration, without trusting the operator's own logs.

   The WIMSE AI Identity Management System [I-D.ietf-wimse-aims]
   describes how agent identities are established, credentials
   provisioned and authorization decisions made.  It requires tamper-
   evident audit logs with a minimum set of fields (Section 11) but
   leaves the format of those logs open; it states that posture evidence
   formats (Section 8), the policy model and document format
   (Section 12) and compliance criteria (Section 13) are out of scope.
   The audit architecture in [I-D.kuehlewind-audit-architecture]
   identifies SCITT Signed Statements, Receipts and Transparent
   Statements as the canonical artifacts for non-repudiable custody of
   audit records and lists a SCITT registration policy profile as a work
   item.  This document is a concrete proposal for that profile.

   Several individual drafts already profile SCITT for agent actions
   (Section 13).  Each records that an action happened and its
   disposition.  Four gaps remain that this profile addresses:

   1.  An identity that a party other than the operator vouches for,
       bound to a per-call evidence chain.  A workload identifier proves
       which software is making a call, but the operator of that
       software issues it to itself, within its own trust domain.  It
       does not say which agent the software is, who is accountable for
       it, or whether it is the agent that was assessed, and an agent
       that runs in several environments has several unrelated
       identifiers (Section 3.1.2 of [I-D.ietf-wimse-arch]).  This
       profile separates a long-term agent identity, issued by an Agent
       Registration Authority that Relying Parties accept, from the
       runtime identities under which the operator's software
       authenticates (Section 4).  An Agent Credential Statement records
       which runtime identities belong to the agent, and every Execution
       Receipt carries the runtime identifier, the preceding record hash
       and optionally a per-call agent signature, so that a chain of
       receipts is bound to one registered agent and cannot be spliced.

   2.  Integrity of instruction files, system prompts and tool
       manifests.  An agent's behaviour is determined as much by its
       system prompt, instruction files, skills, hooks, tool manifests
       and memory as by its model, and injection through these inputs,
       including through invisible Unicode, is a documented attack
       class.  This profile defines a Configuration Integrity Statement
       that commits to digests of the static inputs after mandatory
       Unicode normalization, requires every Execution Receipt to
       reference the configuration in force, and commits to the state of
       memory at the start and end of each Task.

   3.  Revocable operational assurance bound to running evidence, under
       supervision.  An assessment is useful only while the assessed
       identity, capabilities, policy, configuration and deployment

       remain applicable.  This profile binds an Assurance Statement to
       those values, records its risk basis and monitoring coverage, and
       lets a Supervisory Authority, separate from the assessor,
       restrict, suspend or withdraw it.

   4.  Evidence where a call is received, and across calls between
       agents.  Agents increasingly call services operated by other
       parties, and those services are increasingly agents themselves.
       A request can pass through several agents, each run by a
       different operator, before it reaches the system that acts on it.
       For example, an assistant acting for an individual asks a
       platform's agent to file an application; that agent queries a
       records service; the records service calls an identity-
       verification service.  Records produced only on the calling side
       cannot support the decision made on the serving side, and records
       kept separately on each side cannot show that they describe the
       same call.

   A Serving Party decides on every call whether to act.  It is the only
   party that can apply its own conditions whatever the caller's
   operator does, but it sees one call at a time and not the history
   that led to it.  The decision is made per call, not per session or
   per credential, because what it depends on changes between calls: an
   agent's assurance can be suspended within minutes, one agent can act
   for many Principals with different permissions, and operations on the
   same service carry different risk.  This profile therefore defines an
   admission record that a Serving Party produces for every call it
   receives, stating what it checked and what it decided.  That record
   is the Serving Party's evidence of its own conduct and gives an
   auditor a second, independent record of the call.  Only the caller's
   record shows why a call was made; only the Serving Party's record
   shows what was admitted and on what basis; comparing the two, when
   both parties' chains are verified together, shows a call that either
   side omitted.

   When a request passes through intermediaries, four questions need
   answers that no single hop's record supplies: which agent originated
   the request and for which Principal; whether any intermediary used
   authority broader than that Principal's; whether suspending an agent
   stops the work it started further along; and which operator's agent
   did what.  The WIMSE architecture requires that "each hop in the
   chain MUST explicitly scope and re-bind the security context" and
   that autonomous actions "MUST be clearly distinguished from delegated
   ones" (Section 3.4.11 of [I-D.ietf-wimse-arch]).  This profile links
   each hop's records to those of the hop before it and carries the
   principal of the transaction, a transaction identifier and the
   sequence of acting agents with the request, so that a verifier can
   answer these questions from evidence rather than from the operators'
   accounts.

   A declared objective, attested runtime and guardrails do not
   constrain every means an agent may choose.  During a 2026 cyber-
   capability evaluation, agents created an unsanctioned coordination
   channel, pursued scorer tampering, crossed task boundaries and
   investigated altering their traces [METR-HF].  This motivates third-
   party review of whether capabilities and controls are proportionate
   to purpose.

   Monitoring is a distinct safeguard after assessment: for highly
   autonomous or otherwise higher-risk agents, it checks observed
   operation against the assessed scope and approved controls and
   supports reassessment, suspension or withdrawal.  Article 72 of
   [EUAIACT] requires proportionate lifetime monitoring for legally
   classified high-risk AI systems.  This profile's higher_risk value is
   not that legal classification and does not establish compliance.

   This document is a profile of [RFC9943] and [RFC9942].  It does not
   change the SCITT architecture and does not define an identifier
   scheme, how a registry or Supervisory Authority is established, a
   policy language or an accreditation scheme.

2.  Terminology

   This document uses the terms Artifact, Issuer, Receipt, Registration,
   Registration Policy, Relying Party, Signed Statement, Statement,
   Transparency Service (TS), Transparent Statement and Verifiable Data
   Structure (VDS) as defined in Section 3 of [RFC9943]; Workload, Trust
   Domain and Workload Identity Credential as defined in Section 2 of
   [I-D.ietf-wimse-arch]; Actor and Delegation as in Sections 1.1 and
   4.1 of [RFC8693]; and Call Chain and Transaction as defined in
   Section 3 of [I-D.ietf-oauth-transaction-tokens], except that a Call
   Chain here may cross Trust Domains.  The principal of the transaction
   is the subject named by the sub claim of a Transaction Token
   (Section 9.2 of [I-D.ietf-oauth-transaction-tokens]).  This profile
   uses delegation semantics only, never impersonation.

   The terms below are either profiled from existing IETF vocabulary, as
   stated in each definition, or introduced by this document.  Agent
   Registration Authority, Calling Agent, Caller Reference, Linked
   Evidence Chains, Linked Verification, Principal Link, Responsible
   Entity, Serving Party, Sub-agent and Supervisory Authority have no
   equivalent in the IETF specifications cited here.

   Actor Chain:  The ordered list of Actors that have acted on a
      request, least recent first.  It is the list form of a chain of
      delegation expressed by nested act claims (Section 4.1 of
      [RFC8693]): the most deeply nested act is the first entry and the
      outermost act, the current actor, is the last.  The term "actor
      chain" is used in Section 3.4.9 of [I-D.ietf-wimse-arch].

   Admission:  The authorization decision a Serving Party makes for one
      call, recorded as an Execution Receipt of type admission
      (Section 6.7.2).  It is a policy decision in the sense of
      [RFC3198], made per call and recorded.

   Agent:  A workload whose behaviour is driven, in whole or in part, by
      a non-deterministic decision process (typically an LLM) and that
      invokes tools, services or resources, as in Section 4 of
      [I-D.ietf-wimse-aims].

   Agent Assurance Assessor:  A SCITT Issuer that evaluates an agent and
      issues Assurance Statements (Section 6.8).  It MAY be the
      Responsible Entity at assurance levels 1 and 2.  At levels 3 and 4
      it MUST be a Third-Party Agent Assurance Assessor.

   Agent Registration Authority:  A SCITT Issuer that issues long-term
      agent identities: it verifies the Responsible Entity, records what
      was declared for the agent, assigns the logical_agent_id and
      lineage_id, and maintains the registration's status (Section 4).

      How an authority is established is out of scope.  The name is
      unrelated to SCITT Registration, which is the act of entering a
      Signed Statement into a TS.

   Bundle:  A self-contained set of Transparent Statements and Execution
      Receipts sufficient for offline verification of a segment of an
      Evidence Chain (Section 8).

   Caller Reference:  The member of an admission receipt that identifies
      the Calling Agent's Execution Receipt for the same call
      (Section 6.7.3).

   Calling Agent, Serving Party:  For a given call, the agent that makes
      it, and the workload, possibly itself an agent, that receives it
      and decides whether to act on it.  These are roles in one call,
      not kinds of agent: an agent is a Serving Party for the call it
      receives and a Calling Agent for the calls it then makes.  In the
      terms of [RFC8693], the Calling Agent is the current actor.  A
      Serving Party that verifies evidence before admitting a call acts
      as a Relying Party.

   Capability Profile:  The operator's declaration of an agent's purpose
      and effective model, tool, data, permission and delegation scope,
      including the functions of any Sub-agents, committed to by digest
      at registration and in an Assurance Statement.

   Decision Point:  A point at which a call is intercepted, a policy
      decision taken and enforced, and an Execution Receipt produced.
      It combines a Policy Decision Point and a Policy Enforcement Point
      ([RFC3198]) and adds recording.  In a Harness these are the model
      door (every inference) and the tool door (every tool invocation,
      its result and any resulting egress); at a Serving Party, the
      ingress door (every call received).

   Evidence Chain:  An ordered sequence of Execution Receipts, each
      carrying the hash of its predecessor, scoped to one Agent
      Credential or Serving Party Credential Statement (Section 6.7.1).

   Evidence Service:  The service, operated by or for the Harness or
      Serving Party operator, that issues Execution Receipt and
      Execution Epoch Statements and registers them with a TS; the SCITT
      Issuer for those statements.

   Execution Receipt:  A single record produced at a Decision Point
      (Section 6.7); registered with a TS, individually or through an
      epoch root, it becomes an Execution Receipt Statement.

   Harness:  The runtime that hosts an agent, mediates its calls to

Internet-Draft          Agent Execution Evidence            October 2026


      models and tools, and operates the Decision Points.

   Linked Evidence Chains, Linked Verification:  The Evidence Chains of
      the parties to one Call Chain, linked through Caller References;
      and their verification together (Section 9.1).

   Logical Agent, Runtime Identity:  The persistent identity of an agent
      across environments, named by a logical_agent_id issued by an
      Agent Registration Authority; and a workload identifier
      (Section 3.1.2 of [I-D.ietf-wimse-arch]) under which the agent
      authenticates in one Trust Domain for one period.  A Logical Agent
      is a logical workload in the sense of Section 2 of
      [I-D.ietf-wimse-arch] that is an agent.  One Logical Agent MAY
      have several Runtime Identities.

   Operational Assurance:  Time-bounded confidence that an identified
      agent's assessed capabilities, deployment and controls remain
      within their approved scope, based on assessment and, where
      required, continuing monitoring.

   Policy Pack:  A versioned document that configures Decision Points,
      layered by digest reference to a parent (Section 6.5).  The policy
      document format is out of scope.

   Principal:  The natural person, organization or workload on whose
      behalf an agent acts for a given Task.  It is the "delegated
      subject (user or system)" of Section 11 of [I-D.ietf-wimse-aims],
      and is used as in Section 1.1 of [RFC8693].

   Principal Link:  A digest that lets the two parties to a call show
      that they recorded the same Principal without revealing it
      (Section 6.7.3).

   Responsible Entity:  The legal or natural person accountable for a
      Logical Agent, as registered in its Agent Registration Statement.

   Sub-agent:  An agent instantiated by another agent, its parent, to
      perform a declared function within the parent's Tasks.  A Sub-
      agent has no Logical Agent identity of its own and acts under its
      parent's (Section 6.3.1).

   Supervisory Authority:  The Issuer that a Relying Party's or TS's
      policy designates for a scheme named by scheme_id.  It publishes
      the scheme, holds the status of Assurance Statements issued under
      it, and alone restricts, suspends or withdraws them
      (Section 6.8.2).

   Task:  A unit of agent work delimited by task_start and task_end

      Execution Receipts and named by the seq of its task_start.

   Third-Party Agent Assurance Assessor:  An Agent Assurance Assessor
      that is organizationally independent of the Responsible Entity and
      agent operator, and whose identity and signing key a Relying Party
      accepts under its trust policy.  This profile-specific role can
      perform the RATS Verifier role or consume Attestation Results from
      an accepted RATS Verifier, but also assesses the agent's
      capabilities, deployment and controls.  Existing IETF
      specifications do not define qualification, independence-testing
      or accreditation criteria for this role.

   This profile defines eleven Signed Statement types: Agent
   Registration, Model Provider, Agent Credential, Serving Party
   Credential, Policy Pack, Configuration Integrity, Configuration
   Drift, Execution Receipt, Execution Epoch, Assurance and Revocation
   Statements (Section 6.1 to Section 6.8).

3.  Identifiers

   This profile imports identifier schemes and does not define one.

   logical_agent_id:  MUST be a did:web identifier [DID-WEB] whose
      domain name, the first component of the method-specific identifier
      after percent-decoding, equals the host component of the iss of
      the Agent Registration Statement that assigned it, for example
      did:web:register.example:agent:a1b2c3 issued by
      https://register.example.  The identifier itself thus shows which
      authority vouches for the agent.

   Runtime Identity:  SHOULD be a Workload Identifier as defined in
      [I-D.ietf-wimse-identifier] (the spiffe or wimse scheme).
      Section 6 of [I-D.ietf-wimse-aims] requires that an agent be
      assigned exactly one WIMSE identifier; within any one such
      deployment, that identifier is the agent's Runtime Identity there,
      and the Logical Agent sits above the Runtime Identities of all its
      deployments.

   service_id:  A URI under a domain that the Serving Party controls,
      using the https, spiffe, wimse or did:web scheme.

   Implementations MUST treat all identifiers as opaque strings for
   comparison purposes; two identifiers are equal if and only if their
   octet sequences are equal.

   The CWT Claims header parameter (label 15) required by Section 6 of
   [RFC9943] MUST carry the Issuer in iss (label 1).  In sub (label 2),
   Agent Credential, Configuration Integrity, Configuration Drift,

   Execution Receipt and Execution Epoch Statements carry the applicable
   Runtime Identity (or service_id); Agent Registration and Assurance
   Statements carry logical_agent_id; Serving Party Credential
   Statements carry service_id; Model Provider Statements carry
   model_id; Policy Pack Statements carry pack_id; and Revocation

   A Principal is carried as a claim inside the statement payload, not
   in the COSE header, because a Principal is not an Artifact subject in
   the SCITT sense and because the header is visible to the TS.  A
   Principal of kind natural person MUST be represented by a 32-octet
   digest computed as SHA-256 over the concatenation of a pepper held by
   the statement's Issuer and the canonical identifier of the person
   (Section 10).  A Principal of kind organization or workload MAY be
   represented in clear text.

4.  Agent Identification

   A Relying Party that must decide whether to act on an agent's
   request, or hold someone accountable afterwards, needs an identity
   that persists across environments and that a party other than the
   operator vouches for.  This profile obtains it in the following
   steps.

   1.  Declaration.  The operator submits to an Agent Registration
       Authority the agent's Capability Profile and, for each model in
       it, the Model Provider Statement (Section 6.2) where the provider
       has issued one.  The Capability Profile identifies each model by
       a dated version identifier and, where available, by the digest of
       that statement.

   2.  Verification.  The authority verifies the Responsible Entity by
       its own identity-proofing procedures, which are out of scope.  It
       SHOULD require the operator to prove possession, at registration,
       of the agent key it will name in its first Agent Credential
       Statement.

   3.  Registration.  The authority issues an Agent Registration
       Statement (Section 6.1) assigning the logical_agent_id and
       lineage_id and committing to what was declared, and registers it
       on a TS.  The registered statement is the authoritative record of
       the agent's identity.

   4.  Operation.  The operator issues Agent Credential Statements
       (Section 6.3) that reference the registration and list the
       agent's Runtime Identities, key, Harness, model binding and Sub-
       agents.  These change as the agent moves between environments and
       its keys rotate; the registration does not.



Thaha & Shamsudeen         Expires 1 May 2027                  [Page 11]

Internet-Draft          Agent Execution Evidence            October 2026


   5.  Status.  The authority maintains the registration's status in a
       Token Status List [I-D.ietf-oauth-status-list] and ends it, where
       required, with a Revocation Statement: reason code 5 (closed) for
       administrative retirement and 3 (withdrawn) for an adverse
       finding.

   6.  Change and lineage.  A change to the declared Capability Profile,
       or a new Model Provider Statement for a model in it, requires a
       superseding Agent Registration Statement with the same
       logical_agent_id and lineage_id, and reassessment; the authority
       MUST revoke the superseded registration with reason code 2
       (superseded), so that credentials naming it cease to verify.  A
       change of Responsible Entity, for example on a transfer between
       organizations, requires a new registration with a new
       logical_agent_id and the same lineage_id; the previous
       registration is closed, and the agent MUST be reassessed before
       use.  The lineage_id keeps the history of earlier registrations,
       adverse entries included, linked to the agent.

   A Relying Party is configured with the set of Agent Registration
   Authorities it accepts.  An agent registered by an authority in
   another jurisdiction is verified identically and accepted only if
   that authority is in the set; how authorities come to recognize one
   another is out of scope.  An organization MAY act as the Agent
   Registration Authority for its own agents; whether a Relying Party
   accepts it is a matter of policy.

   An Agent Registration Authority MAY also publish registrations
   through other channels.  Such channels are not authoritative: the
   registered statement and its status prevail.

5.  Common Encoding

   Each statement type defined here is a CBOR map with integer keys.
   Hash algorithm identifiers are taken from the IANA COSE Algorithms
   registry.  The CDDL in this document uses the conventions of
   [RFC8610].  Every payload is encoded with the deterministic encoding
   rules of Section 4.2.1 of [RFC8949] ("canonical CBOR" below).

   aee-statement = agent-credential / policy-pack / config-integrity
                 / config-drift / execution-receipt / execution-epoch
                 / assurance / revocation / agent-registration
                 / serving-party-credential / model-provider

   aee-type = &(
     agent-credential:          1,
     policy-pack:               2,
     config-integrity:          3,



Thaha & Shamsudeen         Expires 1 May 2027                  [Page 12]

Internet-Draft          Agent Execution Evidence            October 2026


     config-drift:              4,
     execution-receipt:         5,
     execution-epoch:           6,
     assurance:                 7,
     revocation:                8,
     agent-registration:        9,
     serving-party-credential: 10,
     model-provider:           11
   )

   ; A digest is a COSE hash algorithm identifier and the digest value.
   ; SHA-256 is -16 in the IANA COSE Algorithms registry.
   digest = [ alg: int, value: bstr ]

   validity = {
     1 => uint,    ; nbf, seconds since the Unix epoch
     2 => uint     ; exp, seconds since the Unix epoch
   }

   principal = {
     1 => principal-kind,  ; kind
     2 => bstr / tstr,  ; id: 32-octet digest for natural persons,
                        ; otherwise an identifier
     ? 3 => principal-assurance,  ; principal_assurance
     ? 4 => delegation-ref        ; delegation_ref
   }
   principal-kind = &( natural-person: 1, organization: 2, workload: 3 )

   ; How strongly the Principal was verified, as a Vector of Trust
   ; (RFC 8485): the vector (at least its identity proofing
   ; component) and the trustmark URL of the trust framework
   ; that defines the values.
   principal-assurance = {
     1 => tstr,         ; vot, for example "P2"
     2 => tstr,         ; vtm, trustmark URL
     ? 3 => tstr        ; verifier: who performed the proofing
   }

   ; The Principal's grant of authority to this agent.
   delegation-ref = {
     1 => digest,       ; token_digest of the delegation token
     ? 2 => status-ref  ; status of this delegation
   }

   In the JSON form, kind determines whether id is a base64url digest or
   a clear-text identifier. principal_assurance records how strongly the
   Principal's identity was verified, using the identity proofing
   dimension of Section 2.1 of [RFC8485]; each jurisdiction's trust



Thaha & Shamsudeen         Expires 1 May 2027                  [Page 13]

Internet-Draft          Agent Execution Evidence            October 2026


   framework, named by the trustmark, defines the values, so that
   Principals proofed under different trust frameworks are recorded by
   the same mechanism. delegation_ref lets one Principal's delegation be
   revoked without revoking the agent: its status entry is maintained by
   whoever granted the delegation.  Both are fixed for a Task, as the
   rest of principal is (Section 6.7.1).

   No statement defined here contains a floating-point value, and an
   Issuer MUST NOT emit one, including NaN or an infinity.  Text strings
   MUST be valid UTF-8.  A payload that violates either rule, or that
   has duplicate map keys, is malformed: an Issuer MUST NOT repair it
   before signing or hashing, and a TS or Relying Party MUST reject it.

   Each statement is carried as the payload of a COSE_Sign1 Signed
   Statement per Section 6 of [RFC9943].  The protected header MUST
   contain alg (label 1); content type (label 3) set to application/aee-
   statement+cbor or application/aee-statement+json; kid (label 4), x5t
   (label 34) or x5chain (label 33) per Section 6 of [RFC9943]; and the
   CWT Claims header parameter (label 15) with iss, sub and the aee_type
   claim (Section 12.2), whose value MUST equal key 1 of the payload.
   Duplicating the type in the header lets a TS apply type-specific
   Registration Policy (Section 7) from the non-opaque header, as
   Section 3 of [RFC9943] requires, without parsing the payload.

5.1.  JSON Alternative Encoding

   A statement MAY instead be encoded as a JSON object.  Each integer
   key is replaced by the member name given for it in the CDDL comment
   of its type (for example key 7 of an Execution Receipt is
   policy_pack_digest); group names such as principal, harness,
   model_binding, validity, runtime_identities and assessed_scope name
   nested objects, and enumerated values use the lowercase names of
   their CDDL group.  Byte strings are base64url without padding, and a
   digest is an object {"alg": <name>, "value": <base64url>} where
   <name> is a hash name from the IANA "Named Information Hash Algorithm
   Registry" (for example "sha-256").  The JSON form MUST be I-JSON
   [RFC7493], which excludes lone surrogates and duplicate member names,
   and integers in it MUST NOT exceed 2^53 - 1 in absolute value.
   Before signing or hashing, it MUST be canonicalized with [RFC8785].
   The content type is application/aee-statement+json.  A single
   Evidence Chain MUST use one encoding throughout.

6.1.  Agent Registration Statement

   An Agent Registration Statement is the authoritative record of a
   Logical Agent's identity (Section 4).  Its Issuer is an Agent
   Registration Authority.

   agent-registration = {
     1 => 9,                   ; aee-type
     2 => tstr,                ; logical_agent_id (see {{ids}})
     3 => principal,           ; responsible_entity
     4 => tstr,                ; lineage_id
     5 => digest,              ; capability_profile_digest, as declared
     6 => [ * digest ],        ; provider_statement_digests
     7 => validity,            ; validity
     ? 8 => status-ref,        ; status: Token Status List reference
     ? 9 => tstr,              ; scheme_id: registration scheme (URI)
     ? 10 => digest            ; prior_registration_digest
   }

   capability_profile_digest commits to the Capability Profile the
   operator declared, and provider_statement_digests to the payloads of
   the Model Provider Statements it references. lineage_id is an opaque
   identifier assigned by the authority that outlives logical_agent_id.
   prior_registration_digest names the registration this one supersedes
   or, on a change of Responsible Entity, follows.  A natural-person
   responsible_entity is hashed with a pepper held by the authority
   (Section 10).

6.2.  Model Provider Statement

   A Model Provider Statement records what a model provider states about
   one version of a model.  Its Issuer is the model provider.  An
   operator SHOULD reference one for every model in its Capability

   scheme or a Relying Party MAY require it.

   model-provider = {
     1 => 11,                  ; aee-type
     2 => tstr,                ; model_id: dated version identifier
     3 => tstr,                ; provider
     ? 4 => digest,            ; weights_digest
     5 => digest,              ; evaluations_digest
     6 => digest,              ; safeguards_digest
     7 => [ + tstr ],          ; permitted_uses
     ? 8 => digest,            ; training_data_summary_digest
     ? 9 => digest,            ; change_commitments_digest
     10 => uint                ; iat, seconds since the Unix epoch
   }

   model_id MUST be a dated version identifier, never an alias that the

   retained by the provider; their formats are out of scope.  A new

6.3.  Agent Credential Statement

   An Agent Credential Statement binds an agent identifier to the public
   key the agent uses for per-call signatures, to the Principal it acts
   for, to the Harness that hosts it, and to how its model is bound.  It
   also records the agent's identity continuity: which registered
   Logical Agent this runtime is an instance of, and under which Runtime
   Identities it and its Sub-agents may appear.  Its Issuer is the
   Harness operator or the identity provider that issued the agent's
   workload credential.

   The continuity fields exist because workload identifiers do not, by
   themselves, say what they name.  Section 3.1.2 of
   [I-D.ietf-wimse-arch] states that a workload identifier "MAY
   represent a logical workload, a service implemented by one or more
   workloads, or a specific workload instance, depending on deployment
   policy", and that "two credentials containing the same workload
   identifier value represent the same workload only when validated
   under the same trust domain and issuer trust configuration".  An
   agent that moves between a development cluster, a production cluster
   and a cloud identity platform acquires a different identifier in
   each, meaningful only within its trust domain.  A Relying Party
   cannot correlate those identifiers by inspection.  This profile
   therefore records the mapping from a Logical Agent to its Runtime
   Identities as a signed, registered statement, and verifies receipts
   against it, rather than assuming correlation.

   agent-credential = {
     1 => 1,                   ; aee-type
     2 => tstr,                ; agent_id (see {{ids}})
     3 => COSE_Key,            ; agent_key, RFC 9052 Section 7
     4 => principal,           ; principal
     5 => harness,             ; harness
     6 => model-binding,       ; model_binding
     7 => validity,            ; validity
     ? 8 => tstr,              ; credential_ref: identifier of the
                               ; workload credential (e.g. WIT jti,
                               ; certificate thumbprint) this binds to
     9 => tstr,                ; logical_agent_id

Internet-Draft          Agent Execution Evidence            October 2026


     10 => principal,          ; responsible_entity
     11 => [ + runtime-identity ],  ; runtime_identities
     12 => lifecycle-class,    ; lifecycle_class
     13 => digest,             ; registration_digest: digest of the
                               ; Agent Registration Statement payload
     ? 14 => [ + subagent ],   ; subagents
     ? 15 => [ + tstr ]        ; hosts (see {{serving}})
   }

   runtime-identity = {
     1 => tstr,                ; identifier
     2 => id-scheme,           ; scheme
     3 => tstr,                ; trust_domain
     4 => uint,                ; valid_from, seconds since Unix epoch
     5 => uint                 ; valid_until
   }
   id-scheme = &( wimse: 1, spiffe: 2, did: 3, oidc: 4,
                  cloud-native: 5, other: 6 )
   lifecycle-class = &( ephemeral: 1, persistent: 2 )

   subagent = {
     1 => tstr,                ; subagent_ref, unique within the parent
     2 => tstr,                ; function, as declared
     ? 3 => COSE_Key,          ; subagent_key
     ? 4 => [ + runtime-identity ]  ; runtime_identities
   }

   harness = {
     1 => tstr,                ; name
     2 => tstr,                ; version
     ? 3 => digest             ; digest: of the harness binary/image
   }

   model-binding = {
     1 => binding-mode,        ; mode
     ? 2 => digest,            ; weights_digest (mode 1 only)
     ? 3 => tstr,              ; model_id as named by the provider
     ? 4 => tstr,              ; provider
     ? 5 => bstr,              ; tee_evidence: digest of or reference
                               ; to RATS Evidence (mode 3 only)
     ? 6 => digest             ; provider_statement_digest
   }
   binding-mode = &( weights-digest: 1, api: 2, api-tee: 3 )

   The binding modes have the following meaning. weights-digest: the
   Harness loads the model locally and weights_digest commits to the
   weights. api: the model is invoked through a remote API; only
   model_id and provider are known. api-tee: as api, but the provider

   supplies attestation Evidence for the serving environment, referenced
   by tee_evidence.  Relying Parties MUST NOT infer from mode api
   anything about which model actually served a request; only the
   provider's claim is recorded.

   registration_digest names the Agent Registration Statement in force.
   logical_agent_id and responsible_entity MUST equal those of that
   registration. provider_statement_digest, where present, names the
   Model Provider Statement for the bound model and MUST be among the
   registration's provider_statement_digests. runtime_identities lists
   every identifier under which the agent may produce Execution Receipts
   while this credential is valid, each with its scheme, trust domain
   and validity window.  The agent_id in key 2 MUST appear in
   runtime_identities. lifecycle_class is ephemeral for an agent
   instantiated for one Task and persistent for a long-running agent.
   subagents lists the Sub-agents the agent may instantiate
   (Section 6.3.1). hosts is used only where the agent is a Serving
   Party.  It has the meaning and the form defined for the Serving Party
   Credential Statement in Section 6.4, and the same rule applies: it
   MUST be present in an Agent Credential Statement whose Evidence Chain
   contains an admission receipt that carries call_digest.  An agent
   that only calls other parties needs no hosts.

   An Agent Credential Statement is valid for Execution Receipts whose
   ts lies within its validity.  Rotation of the agent key is performed
   by registering a new Agent Credential Statement; the old statement
   remains valid for receipts within its own window.

6.3.1.  Sub-agents

   A Sub-agent acts under its parent's identity and credential; it is
   not separately registered.  Each function a Sub-agent may perform
   MUST be declared in the parent's Capability Profile, so that the
   assessment covers it, and each Sub-agent MUST be listed in the
   parent's Agent Credential Statement with a subagent_ref unique within
   the parent and its declared function.  A Sub-agent that runs as a
   separate workload SHOULD have its own subagent_key and Runtime
   Identities, so that compromise of one Sub-agent does not expose the
   parent's key.  Every Execution Receipt produced for a Sub-agent
   carries subagent (Section 6.7), so that each action is attributable
   to a specific Sub-agent and function.  A Sub-agent's work is a Task
   delegated from a Task of its parent (Section 6.7.1).  An agent that
   outlives its parent, or that serves other agents, is not a Sub-agent
   and MUST be registered in its own right.

6.4.  Serving Party Credential Statement

   A Serving Party that is itself an agent uses its Agent Credential
   Statement.  A Serving Party that is not an agent scopes its Evidence
   Chain with a Serving Party Credential Statement, whose Issuer is the
   Serving Party's operator.

   serving-party-credential = {
     1 => 10,                  ; aee-type
     2 => tstr,                ; service_id (see {{ids}})
     3 => COSE_Key,            ; service_key
     4 => principal,           ; responsible_entity
     5 => validity,            ; validity
     ? 6 => [ + runtime-identity ],  ; runtime_identities
     ? 7 => [ + tstr ]         ; hosts
   }

   The agent_id of each receipt in the chain carries the service_id or
   one of the listed runtime_identities.  A Serving Party Credential is
   not registered by an Agent Registration Authority; the Serving Party
   identifies itself under its own domain.

   hosts lists every host under which callers may reach the service,
   including the names of fronting gateways and proxies.  Each entry is
   in the form of egress_host (Section 6.7): a lowercase A-label with no
   port.  A caller's egress_host is compared with this list in Linked
   Verification (Section 9.1).  The comparison shows that the caller
   named a host this Serving Party declares.  It does not show which
   service the caller meant when one host fronts several services,
   because each of them lists that host.  Behind a shared host, services
   are told apart by the request-target, which call_digest binds, and by
   the gateway's routing, which this document does not record. hosts
   MUST be present in a Serving Party Credential Statement whose
   Evidence Chain contains an admission receipt that carries
   call_digest; there is no default, and the host of service_id is not
   assumed.  Each entry MUST be a host that the operator controls or has
   delegated to its front end.  The list is the Serving Party's own
   signed declaration; Section 11 says what follows from a false one.

6.5.  Policy Pack Statement

   A Policy Pack Statement commits to the digest of a policy document
   and places it in a lineage.  Its Issuer is the pack author.  The
   format of the policy document is out of scope; the digest is over the
   document bytes as published.

Internet-Draft          Agent Execution Evidence            October 2026


   policy-pack = {
     1 => 2,                   ; aee-type
     2 => tstr,                ; pack_id (URI or opaque name)
     3 => tstr,                ; pack_version
     4 => digest,              ; pack_digest over the pack document
     ? 5 => digest,            ; parent_pack_digest
     6 => layer,               ; layer
     ? 7 => tstr               ; pack_content_type of the document
   }
   layer = &( jurisdiction: 1, sector: 2, institution: 3,
              deployment: 4 )

   Policy Packs form a chain from the most general to the most specific
   layer (jurisdiction, sector, institution, deployment).  A pack with a
   parent_pack_digest MUST have a layer strictly greater than its
   parent's.  A child pack can only tighten: for every Decision Point
   and every input, the decision under the child MUST NOT be less
   restrictive than under any ancestor, with restrictiveness ordered
   block > confirm > record > allow (Section 6.7).  A Relying Party MUST
   walk the parent chain to a root and verify that every pack is
   registered (Section 9); whether a child semantically tightens its
   parent cannot be established offline from digests, and an Assurance
   Statement (Section 6.8) is how a party asserts it.

   config_digest is computed over the canonical CBOR encoding (or the

6.6.1.  Unicode Normalization Before Digesting

   Textual configuration inputs are a vector for instruction injection
   that is invisible to human reviewers.  Before digesting any entry
   whose content is valid UTF-8, an Issuer MUST apply Unicode
   Normalization Form C [UAX15], then process the following code points
   according to the normalization profile, then digest the resulting
   UTF-8 octets: U+200B, U+200C, U+200D (zero width space, non-joiner,
   joiner); U+2060 (word joiner); U+FEFF (including a leading byte order
   mark); U+E0000 to U+E007F (Tags); and the bidirectional controls
   U+202A to U+202E and U+2066 to U+2069.

   Under profile 1 ("strip") the listed code points are removed.  Under
   profile 2 ("reject") their presence is an error and no statement is
   issued until the content is corrected; profile 2 is RECOMMENDED for
   the system_prompt, instruction_file, skill and tool_description
   classes.  Content that is not valid UTF-8 is digested over the raw
   octets.  Normalization is for digesting only; whether the Harness
   also strips these code points from what it presents to the model is a
   Harness matter not asserted by this statement.

   A Configuration Drift Statement SHOULD be issued whenever a new
   Configuration Integrity Statement replaces a previous one for the
   same agent.  Drift is an ordinary event; its significance is for the
   Relying Party to decide.

6.7.  Execution Receipt Statement

   An Execution Receipt is the per-call record.  One is produced at
   every Decision Point for every call, whatever the decision, including
   blocked calls; a refused call is recorded with the record_type of the
   action refused.  Its Issuer, when registered individually, is the
   Evidence Service.

   execution-receipt = {
     1 => 5,                   ; aee-type
     2 => uint,                ; seq, per Evidence Chain, from 0
     3 => bstr .size 32,       ; prev_hash: record-hash of seq-1,
                               ; or 32 zero octets when seq = 0
     4 => record-type,         ; record_type
     ? 5 => uint,              ; parent_seq (see below)
     6 => decision,            ; decision

     7 => digest,              ; policy_pack_digest in force

     ? 5 => digest,            ; registration_digest

   }
   subagent-ref = {
     1 => tstr,                ; subagent_ref
     2 => tstr,                ; function

   }

   The members have the following semantics.

   seq, prev_hash:  Define the Evidence Chain (Section 6.7.1).

   record_type:  task_start and task_end delimit a Task; inference

      record a tool invocation and its result; egress records a network
      connection made by a tool or by the Harness on the agent's behalf;
      admission records a Serving Party's decision on a call it received
      (Section 6.7.2).

      response requested the call; for tool_result, that of the
      corresponding tool_call (for a confirmed call, its allow outcome);
      for egress, that of the tool_call (or inference) that caused it;
      for a task_start caused by an admitted call, that of the admission
      receipt.  It MUST be less than seq and MUST reference a receipt of
      the required type.  This is the causal link between what the model
      asked for and what the Harness did.

   decision:  allow: the call proceeded. block: refused by policy.  At
      the model door a block can follow forwarding when the decision
      depends on the response, for example when the responding model is
      not permitted or concurrent calls exceeded a limit; the response
      is then not passed to the agent. record: proceeded without policy
      evaluation.  A call that the Harness observes only after another
      party executed it, such as a tool a model platform ran server-
      side, MUST be recorded as record, never allow or block, because no
      decision preceded it.

      confirm: policy required confirmation from a Principal or operator
      before the call could proceed.  It appears only on tool_call
      receipts.  A confirm receipt MUST be followed by exactly one
      tool_call receipt with the same parent_seq, target, request_digest
      and Task that records the outcome: allow if confirmation was
      granted, or block if it was refused, not given before its
      deadline, could not be obtained, or was overridden by an operator
      halt.  Until its outcome is recorded, the call is to be read as
      not having proceeded.  An outcome MUST carry confirm_seq naming



Thaha & Shamsudeen         Expires 1 May 2027                  [Page 24]

Internet-Draft          Agent Execution Evidence            October 2026


      the confirm it resolves; a tool_call without confirm_seq is not an
      outcome.  A tool_result for the call MUST NOT precede an allow
      outcome.  A Task MUST NOT end while a confirm in it awaits its
      outcome; when a Task is closed, or the session is lost, with a
      confirm pending, the Evidence Service records the outcome as block
      first.

   confirm_seq:  On an outcome, the seq of the confirm receipt it
      resolves.  It MUST name an earlier confirm receipt with the same
      parent_seq, target, request_digest and Task, and MUST NOT appear
      on any other receipt.

   policy_pack_digest, config_integrity_digest:  The pack_digest and
      config_digest in force at the time of the call.  Both MUST be
      present in every receipt, so that one receipt with its Bundle
      states the rules and configuration it was produced under.

   agent_id:  The Runtime Identity under which the agent, or the Sub-
      agent named by subagent, is authenticating at the time of the
      call.  It MUST be listed, with a validity window containing ts, in
      runtime_identities of the governing Agent Credential Statement or
      of the named Sub-agent's entry in it.  On a Serving Party's chain
      it is the service_id or one of its runtime_identities.  Receipts
      of one chain MAY carry different agent_id values as the agent
      moves between environments; the chain, not the identifier, is the
      unit of continuity.  A Policy Pack MAY require agent_id to be
      constant within a Task.

   request_digest, response_digest:  Digests of the request and response
      octets as seen at the Decision Point: the model request and
      response for inference, the arguments and returned value for tool
      records. response_digest commits to the octets as received, before
      the Harness alters, truncates or withholds anything it passes to
      the agent.  Digests require no parsing: a forwarded call whose
      response is an error, malformed or unparsable MUST still be
      recorded, with response_digest over the octets received, or absent
      if none were received.  Content MUST NOT be included in a receipt
      (Section 10).

   ts:  Time of production.  Receipts in a chain MUST be non-decreasing
      in ts.

   agent_sig:  A COSE_Sign1 with detached payload, signed with the
      credential's agent_key, whose Sig_structure payload is the
      canonical encoding of the receipt map without key 15; its CWT
      Claims carry the agent identifier in iss and sub.  It
      distinguishes a receipt the agent itself authorized from one the
      Harness recorded unilaterally, and MUST be verified when present.

   target, egress_host:  The model_id or tool name, or for admission the
      operation requested; and, for egress, the host connected to.  On a
      tool_call or egress receipt that carries call_digest, egress_host
      is REQUIRED and is instead the host named in the request: the host
      of the authority of the target URI, as the caller intended it.  It
      is not the next network hop.  Behind a forward proxy the host
      connected to is the proxy, every call would record the same host,
      and the service binding of Section 6.7.3 would check nothing.
      Recording the host, not merely the decision, is what makes the
      exfiltration class in Section 11 detectable after the fact.

   caller_agent_id, caller_ref, admission_basis:  See Section 6.7.2 and
      Section 6.7.3.

   actor_chain, principal_link, txn:  The Actor Chain, Principal Link
      and transaction identifier of the call, on a tool_call or egress

      or request correlation identifier" required by Section 11 of
      [I-D.ietf-wimse-aims].

      party, and on an admission receipt, a digest of the request as
      sent (by the caller) or as received (by the Serving Party),
      computed under the binding for the protocol in use.  Unlike
      request_digest, which is over the octets as seen at the Decision
      Point and so differs between the two sides, both sides compute
      call_digest over the same representation.  It is therefore equal
      for one call and different for calls that ask for different
      things.  A receipt that carries it records exactly one request.  A
      receipt for a protocol that has no binding carries no call_digest.
      A Serving Party computes its own value over the request it
      received and never takes it from the evidence presented
      (Section 6.7.2).

      encoding of the array [method, request-target, content-digest].

      subagent_ref and function, which MUST match an entry of the

      example to a Sub-agent (Section 6.7.1).

6.7.1.  Evidence Chain

   The record-hash of an Execution Receipt is SHA-256 over its canonical
   encoding (canonical CBOR, or JCS for the JSON form), including key 15
   when present.  An Evidence Chain is scoped to one Agent Credential or
   Serving Party Credential Statement and MUST begin with a receipt of
   seq 0 whose prev_hash is 32 zero octets.  Each subsequent receipt
   carries in prev_hash the record-hash of the receipt with seq one
   less. seq MUST increase by exactly one.  A receipt whose prev_hash
   does not match is not part of the chain.

   task_seq names the Task: it is the seq of the task_start receipt that
   opened it, and a task_start carries its own seq.  Every other receipt
   MUST name an earlier task_start with decision allow whose Task has
   not ended; a Task has at most one task_end, and no receipt names a
   Task after it.  A receipt's parent MUST belong to the same Task,
   except that the parent of a task_start caused by an admitted call is



Thaha & Shamsudeen         Expires 1 May 2027                  [Page 27]

Internet-Draft          Agent Execution Evidence            October 2026


   that admission receipt; every receipt of a Task MUST carry the
   principal of its task_start.  Receipts of different Tasks MAY
   interleave in one chain.  An admission receipt belongs to no Task:
   its task_seq equals its own seq, and the Task rules do not apply to
   it.

   A Task with delegated_from is a delegated Task.  Its task_start MUST
   name an earlier task_start of a Task that has not ended, and MUST
   carry the same principal as that Task.  Its policy_pack_digest MUST
   equal the parent Task's or name a registered pack whose parent chain
   (Section 6.5) includes the parent Task's pack, so that the delegated
   Task's policy descends from the parent's; that a descendant is
   semantically stricter is asserted as described in Section 6.5.
   Whether its effective scope is no wider than the parent's cannot yet
   be checked mechanically (Section 14).

6.7.2.  Admission

   An Ingress Decision Point produces an admission receipt, with
   decision_point ingress, for every call it receives, whatever the
   decision.  Its decision is allow or block; a refused call is recorded
   as block.  The receipt records:

   *  caller_agent_id: the Calling Agent's identity, where it was
      authenticated on the call;

   *  principal: the Principal asserted by the Calling Agent, as the
      Serving Party validated it, hashed with the Serving Party's pepper
      if a natural person;

   *  target and request_digest: the operation requested and the request
      as received;

   *  call_digest: computed by the Serving Party over the request it
      received;

   *  caller_ref, actor_chain, principal_link and txn, where received
      (Section 6.7.3); and

   *  admission_basis: what the decision relied on.  A Serving Party
      that enforces assurance MUST record it on every allow, with the
      Assurance Statement and level relied on, the registration, and
      when the status was checked and the value observed; it SHOULD also
      record a digest of the token presented.

   A Serving Party MUST NOT admit an operation beyond what its policy
   permits for the principal of the transaction and for every Actor in
   actor_chain.  This goes beyond Section 4.1 of [RFC8693], under which



Thaha & Shamsudeen         Expires 1 May 2027                  [Page 28]

Internet-Draft          Agent Execution Evidence            October 2026


   prior actors are informational only: under this profile a Serving
   Party evaluates every Actor, because authority that widened at any
   hop is not narrowed by later ones.  The status of the Calling Agent's
   Assurance Statement and registration MUST be no older than the
   freshness the Serving Party's policy requires when the decision is
   taken.  An agent whose Assurance Statement is RESTRICTED
   (Section 6.8.2) is admitted only for operations within the restricted
   class.

   A Serving Party that receives a cd value with a call
   ([I-D.thaha-wimse-agent-evidence-binding]) computes its own
   call_digest over the request it received, and MUST NOT use the
   presented value.  It MUST refuse the call, recorded as block, when
   the two differ.  A Serving Party MUST refuse a call whose caller_ref
   names a caller receipt that an earlier admission receipt in its own
   Evidence Chain already names, and records the refusal as block.  The
   check and the recording of the admission MUST be atomic, so that
   concurrent requests carrying the same caller_ref cannot both be
   admitted.  The check covers only the Serving Party's own Evidence
   Chain; what other Serving Parties have admitted is not visible to it,
   which is why Section 9.1 also checks the service binding.

   admission_basis.status_checked_at is the time of the status
   observation that the decision relied on.  Where the token's cached
   status was used, it is the token's status_checked_at
   ([I-D.thaha-wimse-agent-evidence-binding]).  It is not the time of
   admission.

6.7.3.  Linking Records Across Calls

   A Calling Agent's tool_call or egress receipt for a call to another
   party carries txn, principal_link and actor_chain.  The Actor Chain
   is the one the Calling Agent received with the request it is serving,
   or empty if it originated the request, with its own agent_id
   appended.  The Serving Party's admission receipt for the call carries
   the same values and a caller_ref naming the Calling Agent's receipt.

   txn, principal_link and actor_chain correlate the two records, but
   only call_digest and the service binding establish that they record
   the same call.  A shared transaction, principal or session is not a
   match.  A match is exact equality of digests over the same
   representation, computed by each side from the request it sent or
   received and never taken from the evidence presented, and a failed
   match is reported separately from verification and correlation
   failures.  This follows the separation of correlation from matching
   in Section 7 of [I-D.schrock-ep-authorization-evidence-chain].  The
   following rules apply:




Thaha & Shamsudeen         Expires 1 May 2027                  [Page 29]

Internet-Draft          Agent Execution Evidence            October 2026


   1.  caller_ref names a tool_call receipt with decision allow (for a
       confirmed call, its allow outcome) or an egress receipt, in
       either case one that carries call_digest, by the Issuer of the
       caller's Evidence Service, its seq and its record-hash.  A
       connection-level egress receipt that does not record a single
       request cannot be named.  At most one admission receipt names any
       one caller receipt.

   2.  The caller receipt's ts is not later than the admission receipt's
       ts plus a clock-skew allowance stated in the Serving Party's
       Policy Pack.

   3.  principal_link is SHA-256 over the octets of the token by which
       the Calling Agent presents the Principal's delegation on the
       call; for HTTP, the access token in the Authorization header
       field, not a Workload Identity Token or proof token.  Both
       parties compute it from the same octets, so they are equal for
       the same call, while neither reveals the Principal.  The caller's
       and the Serving Party's principal values differ when their
       peppers differ.

   4.  txn is equal on both sides and on every receipt the call causes,
       across the whole Call Chain.

   5.  actor_chain is equal on both sides, and its last entry equals
       both the admission's caller_agent_id and the caller receipt's
       agent_id.  A Serving Party that is itself an agent appends its
       own agent_id on the calls it makes in the Task the admission
       caused.

   6.  call_digest is equal on both sides.

   7.  The caller receipt's egress_host is one of the hosts of the
       credential that scopes the Serving Party's chain: its Serving
       Party Credential Statement or, for a Serving Party that is an
       agent, its Agent Credential Statement.  The comparison is between
       the host the caller named and the Serving Party's declaration,
       not between Host values as they arrive, so a gateway that
       rewrites Host does not break it.

   A Calling Agent transmits these values with each call by means
   outside this document; [I-D.thaha-wimse-agent-evidence-binding]
   defines them for HTTP.  Records linked in this way form Linked
   Evidence Chains, verified as in Section 9.1.

6.7.4.  Execution Epoch Statement

   Registering every receipt as its own Signed Statement is permitted
   but is usually impractical.  An Evidence Service MAY instead register
   an Execution Epoch Statement that commits to a contiguous segment of
   the chain.

   execution-epoch = {
     1 => 6,                   ; aee-type
     2 => tstr,                ; agent_id
     3 => uint,                ; first_seq
     4 => uint,                ; last_seq
     5 => bstr .size 32,       ; first_prev_hash: prev_hash of first_seq
     6 => bstr .size 32,       ; last_hash: record-hash of last_seq
     7 => bstr .size 32,       ; epoch_root
     8 => uint                 ; count = last_seq - first_seq + 1
   }

   epoch_root is the Merkle Tree Hash, as defined in Section 2.1.1 of
   [RFC9162] with SHA-256, over the ordered record-hashes of receipts
   first_seq through last_seq.  Because receipts are also hash-chained,
   first_prev_hash and last_hash allow adjacent epochs to be checked for
   continuity without their contents.  A Relying Party in possession of
   a subset of an epoch's receipts verifies them with an inclusion path
   against epoch_root, using the inclusion proof algorithm of
   Section 2.1.3 of [RFC9162].

   Epochs of one chain MUST NOT overlap and MUST be registered in order,
   and all carry in key 2 the agent_id of key 2 of the credential that
   scopes the chain, whatever Runtime Identity individual receipts
   carry, so that the continuity check of Section 7 applies to the whole
   chain.  An Evidence Service SHOULD close an epoch at every task_end
   and at a bounded interval, so that the time between a call and its
   appearance in the TS is bounded.  That interval is an operational
   parameter that a Relying Party MAY require to be stated in a Policy
   Pack.

   The assurance_level value is an Agent Identity Assurance Level
   (AIAL).  These levels grade the assessment of an agent's purpose,
   capabilities, deployment and controls.  They are not the
   Authenticator Assurance Levels of [NIST.SP.800-63-4], do not express
   authentication strength, and SHOULD NOT be abbreviated as "AAL".
   "Identity" is in the name because the levels attach to an identified,



Thaha & Shamsudeen         Expires 1 May 2027                  [Page 34]

Internet-Draft          Agent Execution Evidence            October 2026


   registered Logical Agent (Section 4); they are closest in role to
   that guideline's Identity Assurance Levels, which grade proofing
   before a credential is issued.  Following the same separation, this
   profile treats assessment depth, the strength of the binding between
   an agent and its credential key, and the security of identity
   propagation as independent dimensions.  A level carries no statement
   about how the credential key is protected, nor about how the operator
   was verified; a Relying Party that requires a hardware-bound or
   attested key MUST require it separately in policy, for example
   through accepted RATS Evidence about key storage.  A jurisdiction's
   profile MAY set key-custody and operator-verification requirements
   alongside a minimum level, as separate requirements.

   At levels 3 and 4, the Agent Assurance Assessor MUST be a Third-Party
   Agent Assurance Assessor and MUST include
   independence_declaration_digest, committing to its signed declaration
   that it is independent of the Responsible Entity and the operator.
   Where the registered responsible_entity is an organization, assessor
   MUST also differ from it.  A natural-person responsible_entity is a
   peppered digest that can never equal an assessor identifier, so no
   comparison is made in that case.  Neither the declaration nor
   identifier inequality proves organizational independence; that
   remains a matter for the Supervisory Authority's accreditation of
   assessors.  A Sub-agent has no level of its own: it operates under
   its parent's.  Assessor recognition, suite suitability and
   accreditation remain Relying Party policy; the numbers have no
   meaning beyond this section.

   At levels 3 and 4, accepted RATS Evidence and any resulting
   Attestation Results are the technical runtime evidence base for the
   independent assessment.  The Third-Party Agent Assurance Assessor MAY
   perform the RATS Verifier role or consume Attestation Results from an
   accepted RATS Verifier.  It MUST also evaluate the declared
   capability profile, deployment and controls; acceptance of RATS
   Evidence alone does not establish either level.

   For higher_risk agents, a pass result MUST use level 4, include a
   monitoring_summary, use status checking, and have disposition
   continue.  Before a required monitoring period is complete, the
   result MUST be partial, not pass.  The Agent Assurance Assessor MUST
   issue a replacement statement at the required review frequency.  A
   material change to purpose, capabilities, policy, configuration,
   deployment, controls or identity binding requires reassessment.  A
   Relying Party MUST NOT accept operational assurance from a statement
   whose disposition is reassess, suspend or withdraw; the status and
   withdrawal that follow are set as described in Section 6.8.2 and
   Section 6.8.3.




Thaha & Shamsudeen         Expires 1 May 2027                  [Page 35]

Internet-Draft          Agent Execution Evidence            October 2026


   Higher-risk agents therefore require independent assessment and
   continuing operational monitoring.  Assurance remains valid only
   while the applicable assessment, monitoring and reassessment
   requirements are satisfied.  Each monitoring_summary covers a
   completed observation window, and replacement statements make
   monitoring continuing rather than a one-time probation period.
   Monitoring is an additional safeguard after the initial risk-based
   audit; it does not guarantee that an agent will never act
   maliciously.  Its value depends on what the Harness and external
   evidence sources can observe and how reliably approved controls are
   enforced.

6.8.2.  Supervision

   The party that grants assurance does not monitor and act on its own
   grant: an assessor that suspended or restored its own statement would
   be judging its own decision.  A Relying Party's policy, and where
   applicable a TS's Registration Policy, designates for each scheme_id
   the Issuer that acts as its Supervisory Authority.  Where one is
   designated:

   *  it publishes the scheme, including its risk triggers and the
      deviation classes that require immediate suspension;

   *  the Token Status List referenced by an Assurance Statement under
      the scheme MUST be issued by it;

   *  only it sets RESTRICTED or SUSPENDED, restores VALID, and
      withdraws an Assurance Statement under the scheme; and

   *  the Agent Assurance Assessor issues verdicts and monitoring
      summaries and reports deviations to it.

   A deviation detected during monitoring MUST be reported to the
   Supervisory Authority.  For deviation classes the scheme marks as
   requiring it, the Supervisory Authority MUST suspend at once.  For
   others it MAY first restrict the agent, and suspend once the
   deviation is confirmed, so that a single unverified finding does not
   take an agent offline.  Where no Supervisory Authority is designated,
   the Agent Assurance Assessor performs these functions, and a Relying
   Party MAY refuse assurance under such a scheme.

   RESTRICTED is Status Type 0x03, which Section 7.1 of
   [I-D.ietf-oauth-status-list] reserves as application specific; this
   profile defines its meaning.  A status list that can carry it MUST
   use bits of at least 2.  While a statement is RESTRICTED, a Decision
   Point or Serving Party that enforces assurance MUST refuse operations
   above the risk class the scheme defines for restriction, and SHOULD



Thaha & Shamsudeen         Expires 1 May 2027                  [Page 36]

Internet-Draft          Agent Execution Evidence            October 2026


   let in-flight Tasks reach a safe end.  While a statement is
   SUSPENDED, a Decision Point that enforces assurance MUST refuse
   further model and tool calls by the agent, a Serving Party that
   enforces assurance MUST refuse its calls, and a Relying Party MUST
   NOT accept the agent's operational assurance.  Restriction and
   suspension are lifted only by restoring the status to VALID, or by a
   replacement statement.

   A Supervisory Authority acting beyond its scheme, or whose key is
   compromised, can restrict or suspend any agent assessed under that
   scheme.  Relying Parties accept a Supervisory Authority only for the
   schemes it is designated for.

6.8.3.  Revocation

   An Assurance Statement is revocable by either of two mechanisms, and
   a deployment MUST support at least one: a Token Status List
   [I-D.ietf-oauth-status-list] referenced from key 11, in which status
   0x01 (INVALID) withdraws the statement and 0x02 (SUSPENDED) or 0x03
   (RESTRICTED) limits it (Section 6.8.2); or a Revocation Statement
   registered on the same TS whose subject_digest equals the digest of
   the Assurance Statement payload, issued by the Supervisory Authority
   designated for its scheme or by the Assurance Statement's Issuer.
   Where a Supervisory Authority is designated, the assessor's own
   Revocation Statements are limited to reason codes 1 (key-compromise)
   and 2 (superseded).  A Revocation Statement MAY also revoke an Agent
   Registration, Model Provider, Agent Credential, Serving Party
   Credential or Policy Pack Statement, issued by that statement's
   Issuer.

   Reason code 3 (withdrawn) records an adverse finding.  Reason code 5
   (closed) records an administrative retirement with no adverse
   finding, for example an agent retired by its Responsible Entity or a
   registration that expired without renewal.  An agent is closed by a
   Revocation Statement with reason code 5 that revokes its Agent
   Registration Statement, issued by the Agent Registration Authority at
   the direction of the Responsible Entity or on expiry; the Issuer of
   each of its Agent Credential Statements likewise revokes them.
   Relying Parties MUST NOT treat closed as evidence of misconduct.
   withdrawn and closed are final: a closed or withdrawn agent can
   operate again only under a new registration and a new assessment.
   Restriction and suspension through the status list are the only
   reversible states.

8.  Bundle

   A Bundle is the unit a Relying Party verifies.  It is a CBOR map.

   aee-bundle = {
     1 => [ + Transparent_Statement ],  ; statements (RFC 9943 Sec. 7)
     2 => [ * execution-receipt ],      ; chain segment, ascending seq
     ? 3 => { * uint => inclusion-path },  ; seq => path into its epoch
     ? 4 => [ * bstr .cbor COSE_Sign1 ]    ; Status List Tokens
   }
   inclusion-path = [
     tree-size: uint,
     leaf-index: uint,
     path: [ * bstr .size 32 ]
   ]

   Key 1 MUST contain, as Transparent Statements, the Agent Credential
   or Serving Party Credential Statement, the Agent Registration
   Statement an Agent Credential names, every Policy Pack Statement in
   the lineage of every policy_pack_digest in key 2, every Configuration
   Integrity Statement referenced, every Execution Epoch Statement
   covering a receipt in key 2 (or the receipt's own Transparent
   Statement), and any Assurance and Revocation Statements the producer
   wishes considered.  Key 3 is REQUIRED for any receipt whose epoch is
   not wholly present in key 2.  Key 4 carries a snapshot of each Status
   List Token referenced by an Assurance or Agent Registration
   Statement, or by a delegation_ref, for offline evaluation as of the
   snapshot time.  Model Provider Statements MAY be included.

   A Linked Bundle is an ordered array of Bundles, one for each Evidence
   Chain of a Call Chain, each sufficient on its own, with media type
   application/aee-linked-bundle+cbor.  It is verified as in
   Section 9.1.

   aee-linked-bundle = [ 2* aee-bundle ]




Thaha & Shamsudeen         Expires 1 May 2027                  [Page 40]

Internet-Draft          Agent Execution Evidence            October 2026


   The media type of a Bundle is application/aee-bundle+cbor.  A JSON
   form with the member names statements, receipts, proofs and
   status_tokens, Transparent Statements as base64url COSE_Sign1, has
   media type application/aee-bundle+json.

9.  Verification

   A Relying Party verifies a Bundle by the following steps.  The steps
   are ordered; the first failure terminates verification with the named
   error.  Verification requires the TS's public key(s), the trust
   anchors for Issuers the Relying Party accepts, and the Relying
   Party's own lists of accepted Agent Registration Authorities, Agent
   Assurance Assessors, levels and suites, and of the Supervisory
   Authority designated for each accepted scheme, all obtained out of
   band.  No network access is required.  A verifier that does not
   perform a step MUST NOT report PASS, and input that is malformed at
   any step fails that step rather than leaving the result undefined.

   1.   For every Transparent Statement in key 1, verify every Receipt
        in its receipts header (label 394) per Section 5.2.1 of
        [RFC9942] against a trusted TS key, confirming that the Signed
        Statement is included in the VDS.  On failure: E_RECEIPT_SIG.

   2.   For every Transparent Statement, verify the Issuer's COSE
        signature per [RFC9052] against an Issuer key reached from a
        trust anchor.  On failure: E_ISSUER_SIG.

   3.   For every Transparent Statement, check that the aee_type claim,
        the content type and key 1 of the payload agree and that the
        payload is well-formed.  On failure: E_TYPE_MISMATCH.

   4.   Identify exactly one Agent Credential or Serving Party
        Credential Statement whose Issuer the Relying Party accepts and
        whose identifiers include the agent_id of the first receipt in
        key 2.  Check that no Revocation Statement in the Bundle, from
        the same Issuer, names its payload digest.  On failure:
        E_CREDENTIAL.  For an Agent Credential, identify the Agent
        Registration Statement named by registration_digest, and check
        that its Issuer is an accepted Agent Registration Authority,
        that the domain of its logical_agent_id matches that Issuer
        (Section 3), that its logical_agent_id and responsible_entity
        equal the credential's, that its validity contains every
        receipt's ts, that any status it carries is 0x00 in the Status
        List Token in key 4 as of that token's snapshot, that no
        Revocation Statement from its Issuer names it, and that any
        provider_statement_digest in the credential is among its
        provider_statement_digests.  On failure: E_REGISTRATION.

   5.   For each receipt in key 2, check that its agent_id appears, with

9.1.  Linked Verification

   A Relying Party verifies a Linked Bundle by first verifying each
   Bundle in it by steps 1 to 18, and then, for each admission receipt
   in one Bundle whose caller_ref names a receipt in another, checking
   that:

   1.  the named receipt is present, its record-hash equals
       caller_ref's, its seq matches, and its chain's Evidence Service
       is the Issuer named by caller_ref; on failure, E_CALLER_REF;

   2.  the named receipt and the admission both carry call_digest, and
       the values are equal; on failure, E_CALL_MISMATCH;

   3.  the named receipt's egress_host is present and is among the hosts
       of the credential governing the admission's chain: the Serving
       Party Credential Statement or, for a Serving Party that is an
       agent, the Agent Credential Statement.  A credential without
       hosts fails this check; on failure, E_SERVING_HOST;

   4.  the named receipt is a tool_call with decision allow or an egress
       receipt, in either case one that carries call_digest, no other
       admission names it, and its ts is not later than the admission's
       ts plus the stated skew; on failure, E_CALLER_MISMATCH;





Thaha & Shamsudeen         Expires 1 May 2027                  [Page 44]

Internet-Draft          Agent Execution Evidence            October 2026


   5.  principal_link and txn are present and equal on both receipts; on
       failure, E_PRINCIPAL_LINK;

   6.  actor_chain is equal on both receipts, and its last entry equals
       the caller receipt's agent_id and the admission's
       caller_agent_id; on failure, E_ACTOR_CHAIN;

   7.  where the admission carries admission_basis naming an Assurance
       Statement or registration, that statement is the one the Calling
       Agent's Bundle relies on, at the level recorded; on failure,
       E_ADMISSION_BASIS; and

   8.  where the Serving Party is an agent whose Bundle is in the Linked
       Bundle, every call it makes in the Task the admission caused
       carries the same txn and an actor_chain equal to the admission's
       with its own agent_id appended; on failure, E_ACTOR_CHAIN.

   Checks 2 and 3 follow check 1 so that a mismatch is reported as a
   mismatch and not as a missing receipt.  E_CALL_MISMATCH and
   E_SERVING_HOST are reported separately from the verification errors
   of steps 1 to 18 and from the correlation errors of checks 4 to 8:
   they mean that the named receipt exists, but that the evidence does
   not show that the two records describe the same request sent to the
   same service.

   A caller receipt for a call to another party that no admission in the
   Linked Bundle names, and an admission that names no receipt in it,
   are reported, not failed: the other party's records may simply be
   absent from the Linked Bundle.

9.2.  Meaning of PASS

   A PASS establishes that: the TS committed to each statement in its
   append-only VDS; each statement was signed by the named Issuer; the
   receipts form an unbroken chain sealed into that VDS; every call was
   recorded under a registered policy and configuration; each runtime
   identifier was declared for that time; and, where required, accepted
   identity and operational assurance claims matched the run.  For
   higher-risk assurance, the accepted claim also cites a current
   completed monitoring period and has not been suspended or withdrawn.
   A PASS of Linked Verification establishes, in addition, that each
   linked pair of receipts commits to the same request, as represented
   by call_digest, sent to a host the Serving Party declared, for the
   same Principal, transaction and Actor Chain, by parties each of which
   verified on its own.  It does not establish that the Serving Party is
   the service the caller meant where several services share that host,
   that every hop of the Call Chain is present, that an intermediary
   forwarded the request unchanged in the parts call_digest excludes, or



Thaha & Shamsudeen         Expires 1 May 2027                  [Page 45]

Internet-Draft          Agent Execution Evidence            October 2026


   that a Serving Party checked more than its admission_basis records.

   A PASS does not establish that the Harness recorded every call, that
   a decision was correct, that an api-bound model was the one named,
   that a Policy Pack semantically tightens its parent, that monitoring
   observed every relevant behaviour, or that an Agent Assurance
   Assessor's suite is adequate.  Harness completeness is the
   composition point with remote attestation.  A Harness can produce
   RATS Evidence [RFC9334], for example an EAT [RFC9711] whose
   measurements cover the image named by harness.digest; a Relying Party
   MAY require that Evidence, with the Agent Credential payload digest
   as nonce.  This document does not define that binding.

9.2.1.  Derivable Risk Facts

   Two facts relevant to assurance can be tested from a verified chain
   without any further input, and a Relying Party or an Agent Assurance
   Assessor MAY compute them.  The first is autonomy: over a window, the
   proportion of tool calls that proceeded without confirmation (an
   allow tool_call receipt that is not the outcome of a confirm) to
   those that required it.  A chain in which every consequential tool
   call was confirmed by a Principal describes a different agent from
   one in which none was, even if both passed the same suite.  The
   second is private inference: the model_binding mode of the governing
   credential as it applies to inference receipts.  Mode weights-digest
   with no independent attestation of the runtime means the operator is
   the sole witness to which model ran; mode api-tee, or weights-digest
   accompanied by level 2 or higher attestation, provides a second
   witness.  This document sets no thresholds for either fact; it notes
   that both are derivable so that Policy Packs and Agent Assurance
   Assessors can set them.

10.  Privacy Considerations

   No content:  Execution Receipts carry digests of requests and
      responses, never their content.  Model prompts and tool arguments
      routinely contain personal data; the design keeps that data in the
      operator's custody and places only commitments on the TS.

   Principal hashing:  A natural-person Principal, and a natural-person
      responsible_entity, is represented by SHA-256 over a pepper held
      by the statement's Issuer and the identifier.  The pepper MUST be
      at least 16 octets of entropy, MUST NOT be registered on the TS,
      and SHOULD be rotated per deployment.  The same Principal is
      linkable across receipts of one deployment by design, and not
      across deployments with different peppers.

   Linking across parties:  principal_link lets the two parties to one



Thaha & Shamsudeen         Expires 1 May 2027                  [Page 46]

Internet-Draft          Agent Execution Evidence            October 2026


      call show that they recorded the same Principal without either
      revealing it, because it is a digest of a token both already hold.
      It does not link the Principal across calls unless the same token
      is presented again. txn and actor_chain correlate all hops of one
      transaction and reveal which operators' agents took part; parties
      SHOULD forward them only to the parties they call, and a Serving
      Party SHOULD register epoch roots rather than individual admission
      receipts. caller_ref reveals the caller's Evidence Service to the
      Serving Party.

   Request digests:  call_digest is a digest of request content; where
      that content has low entropy, for example a payment amount sent to
      a known path, a party holding the receipt can confirm a guessed
      value by recomputing the digest.  Registering epoch roots rather
      than individual receipts, as recommended under Retention, limits
      who holds the digest.

   Registration and principal assurance:  An Agent Registration
      Authority can link all agents of one Responsible Entity.
      Resolving a did:web identifier live tells the authority which
      agent is being checked and by whom; verifiers SHOULD rely on the
      registered statement in the Bundle instead. principal_assurance
      reveals how a Principal was verified, which can indicate residence
      or nationality; it SHOULD be carried only where a Serving Party's
      policy requires it.

   Data minimization:  target and egress_host are the only free-text
      members of a receipt and MUST NOT contain query, user, argument or
      parameter-value components; a tool name derived from an HTTP
      operation MAY carry its method and path template.  Issuers MUST
      NOT place Principal identifiers or content in identifiers.
      Purpose, objective, intended-use and risk-tier strings SHOULD use
      concise categories or URIs rather than sensitive operational
      detail.

   Retention:  Statements registered on a TS cannot be removed.
      Operators SHOULD prefer registering epoch roots, which reveal only
      counts and digests, over individual receipts.

   Jurisdictional packs:  A Policy Pack at the jurisdiction or sector
      layer MUST NOT require that Execution Receipts identify natural
      persons in clear text.

   Transparency Service visibility:  A TS sees the protected header of
      every statement: Issuer, agent identifier, type and key
      identifier.  Operators for whom the existence of an agent is
      sensitive SHOULD use opaque identifiers under their own trust
      domain.

11.  Security Considerations

   The security considerations of [RFC9943] and [RFC9942] apply.

   Replay:  A receipt is bound by prev_hash to its position and by
      agent_id and ts to its credential.  Replaying it into another
      chain fails at step 6 of Section 9; replaying it in the same chain
      fails because seq cannot repeat.

   Equivocation:  An operator who shows different chains to different
      Relying Parties is detected because both must be sealed into the
      same non-equivocating VDS (Section 5.1.3 of [RFC9943]), and the
      continuity check in Section 7 refuses the second epoch.  This
      profile relies on the VDS properties and adds nothing to them.

   Omission:  A Harness that does not produce a receipt for a call
      leaves no trace.  Mitigation is outside the chain: attestation of
      the Harness (Section 9), independent recording at the Serving
      Party by admission receipts (Section 6.7.2), and reconciliation of
      egress receipts against network telemetry.  A call recorded by one
      party and not by the other is reported by Linked Verification when
      both chains are present; neither party can remove the other's
      record.

   Confused deputy:  An agent serving several Principals can be induced
      to use one Principal's authority for another's request.  Recording
      the Principal on every receipt of a Task, carrying the Actor
      Chain, and requiring a Serving Party to evaluate every Actor
      (Section 6.7.2) make the substitution visible and let the Serving
      Party refuse it; they do not prevent an agent from misusing
      authority it legitimately holds.

   Forged or replayed caller references:  A caller_ref, actor_chain or


















Thaha & Shamsudeen         Expires 1 May 2027                  [Page 48]

Internet-Draft          Agent Execution Evidence            October 2026


      principal_link received with a call is the caller's claim until
      checked against the caller's registered chain.  A caller_ref
      naming a receipt that does not exist fails E_CALLER_REF.  One
      naming a different real call, for example a payment of another
      amount under the same token and transaction, fails
      E_CALL_MISMATCH, because the two call_digest values differ.  One
      naming the same request sent to a service under a different host
      fails E_SERVING_HOST, because the caller's egress_host is not
      among the hosts the Serving Party declared.  A reference replayed
      to the same Serving Party is refused at admission (Section 6.7.2);
      one replayed to a Serving Party under a different host fails
      E_SERVING_HOST.  Either replay is also reported as
      E_CALLER_MISMATCH when both admissions are in the same Linked
      Bundle, because they name the same caller receipt.  Actors removed
      from or inserted into the chain are detected when the chains of
      all hops are verified together.

   Service declaration:  A Serving Party that lists in hosts a host it
      does not control can be linked to calls meant for that host.  The
      list is a signed claim by the Serving Party, and a Relying Party
      relies on it as it relies on the other claims of the credential.
      Front ends run by other operators are the subject of an open issue
      (Section 14).

   Shared front ends:  One gateway host can front several services, and
      each lists that host in hosts, so E_SERVING_HOST cannot tell them
      apart.  Where the gateway routes on the request path, call_digest
      binds that path, but the mapping from path to service is the
      gateway's own configuration, which a Relying Party trusts and
      which no receipt records.  Two cases remain.  A gateway that
      routes on something call_digest excludes, such as a header or
      tenant identifier, can deliver an identical request to either
      service.  A request that reaches a service without passing through
      the gateway is admitted under the shared host.  In both cases a
      caller reference meant for one service passes Linked Verification
      at the other, unless both admissions are in the same Linked Bundle
      and fail E_CALLER_MISMATCH.  Operators of such gateways SHOULD
      route on the request-target, and services behind them SHOULD
      accept calls only through the gateway.

   Status freshness at admission:  An admission decision based on a










Thaha & Shamsudeen         Expires 1 May 2027                  [Page 49]

Internet-Draft          Agent Execution Evidence            October 2026


      status observation older than the suspension of the agent admits a
      suspended agent.  What matters is the age of the authenticated
      status observation, recorded as status_checked_at, and not the
      remaining lifetime of the token that carries it: a token with
      seconds left can carry an hour-old observation.  A Serving Party
      bounds the age by the freshness its policy requires and SHOULD
      check the status list itself for operations its policy marks as
      high-risk.

   Flooding a Serving Party:  Because a Serving Party records every
      call, including refusals, a caller can inflate its records.
      Serving Parties SHOULD rate-limit before the Ingress Decision
      Point; a call dropped there is not received and produces no
      receipt.

   Memory poisoning:  memory_digest makes changes to memory between
      Tasks visible after the fact; it does not prevent poisoned memory
      from influencing the next Task.  A Policy Pack MAY require review
      of memory changes between Tasks for higher-risk agents.

   Fail-closed evaluation:  A Decision Point that cannot evaluate a call
      MUST NOT let it proceed: for example an input over a size limit, a
      request it cannot parse, a response item it does not recognise, or
      an Evidence Service that cannot be reached.  It MUST NOT evaluate
      a truncated or repaired form of the input instead.  Where the
      Evidence Service is reachable, the refusal is recorded as block.

   Result alteration:  response_digest commits to what the Decision
      Point received, not to what the agent was given.  A Harness that
      rebuilds, truncates or withholds a result before passing it on is
      not distinguishable from the receipt alone.

   Key compromise:  Compromise of the Evidence Service key allows forged
      receipts from the time of compromise; earlier epochs remain
      protected by the TS's Receipts.  Compromise of the agent key
      allows forged agent_sig values but not forged receipts.  Operators
      MUST register a Revocation Statement on compromise and SHOULD use
      short validity windows.

   Identity substitution:  An attacker who obtains a workload identity
      in some trust domain cannot have receipts under it accepted for a
      Logical Agent unless the Agent Credential Statement lists that
      identity for that time (step 5 of Section 9).  Issuers SHOULD keep
      runtime_identities minimal and windows short.

   Session binding:  The Evidence Service MUST authenticate each





Thaha & Shamsudeen         Expires 1 May 2027                  [Page 50]

Internet-Draft          Agent Execution Evidence            October 2026


      Decision Point that submits receipts.  An agent session at a
      Decision Point bound only to a network address protects little,
      since addresses are shared and change.  Sessions SHOULD instead be
      bound to possession of the agent key, for example with a per-
      request proof of possession [RFC9449] or a certificate-bound
      session [RFC8705], so that a captured session identifier is
      useless without the key.

   Principal attribution:  The principal in a receipt is asserted by the
      Evidence Service after it validated the Principal's token; the
      receipt does not carry a proof.  An Evidence Service SHOULD
      retain, outside the receipt, a digest of each token as presented
      and of the key set it was verified with, so that an Auditor can
      repeat the validation.  Token lifetime is judged at validation
      time, not at receipt time, since a Task can outlive the token that
      opened it; any clock-skew allowance MUST be bounded and stated in
      the Policy Pack or the Evidence Service's published configuration.

   Policy downgrade:  Loading a weaker Policy Pack produces receipts
      naming a different policy_pack_digest; a Relying Party that
      requires a specific root pack detects this at step 11.  A Relying
      Party SHOULD reject chains whose policy_pack_digest changes within
      a Task.

   Configuration substitution:  The precedence check at step 12 ensures
      the Configuration Integrity Statement predates the receipts.  The
      Harness MUST compute and compare digests at load time and SHOULD
      re-check them at a bounded interval during a run; a mismatch MUST
      produce a Configuration Drift Statement and a new Configuration
      Integrity Statement before any further receipt.  Blocking calls to
      tools absent from the committed tool manifest (Section 6.6)
      prevents a tool server from evading the commitment by not listing
      a tool.

   Domain allowlist exfiltration:  Allowing egress to a list of trusted
      hosts does not stop exfiltration to an attacker-controlled account
      on an allowed host, or through path and query components.  A
      receipt that records only decision: allow does not help an
      investigator.  This profile therefore requires egress_host in
      egress receipts and request_digest over the full request, so that
      which host received data in which call is answerable from evidence
      rather than from the operator's account.  It does not prevent the
      exfiltration.

   Unicode-based injection:  The rule in Section 6.6.1 makes invisible






Thaha & Shamsudeen         Expires 1 May 2027                  [Page 51]

Internet-Draft          Agent Execution Evidence            October 2026


      code points either irrelevant to the digest (profile 1) or a
      rejection (profile 2).  It does not detect injection through
      visible but misleading text, homoglyphs, or content loaded at
      runtime outside the configuration set.

   Assessment independence:  Level 1 can be self-asserted.  At level 2,
      the Agent Assurance Assessor can still be the Responsible Entity,
      but accepted RATS Evidence adds technical runtime evidence.
      Levels 3 and 4 require a Third-Party Agent Assurance Assessor
      because an operator assessing controls it designed can share their
      assumptions and blind spots.  The presence of an independence
      declaration is checkable, and identifier separation for an
      organization is only a weak signal; organizational independence,
      competence and accreditation are not established by this protocol.

   Supervisory and registration authorities:  Compromise of a
      Supervisory Authority's or Agent Registration Authority's key
      allows agents under it to be suspended, restricted or closed, or
      unregistered agents to appear registered.  Relying Parties accept
      each authority only for the schemes or namespaces it is designated
      for, and the domain-match rule of Section 3 prevents one authority
      from issuing identifiers in another's namespace.

   Transfer without reassessment:  A change of Responsible Entity
      produces a new registration and requires reassessment (Section 4).
      lineage_id lets an authority keep a history of adverse findings
      linked to the agent; it cannot prevent re-registration with
      another authority that does not share that history.

   Sub-agents:  A Sub-agent without its own key signs as its parent, so
      its compromise is its parent's.  A Sub-agent not listed in the
      credential fails verification; whether its declared function is
      within the Capability Profile is checked by the assessor, not by
      the verifier.

   Key binding:  An assurance level and the protection of the credential
      key are independent.  An agent assessed at level 4 whose key is
      held in software can be impersonated by any process that copies
      the key, and its records then carry that level.  Relying Parties
      MUST NOT infer key protection from the level.

   Monitoring limits:  Monitoring detects only deviations visible in its
      declared coverage.  An agent can behave maliciously within an
      approved scope, evade an instrumented Decision Point, or exploit a
      control that is present but ineffective.  Relying Parties MUST
      evaluate coverage, evidence sources, review frequency and control
      enforcement rather than treating level 4 as a guarantee of safe
      behaviour.



Thaha & Shamsudeen         Expires 1 May 2027                  [Page 52]

Internet-Draft          Agent Execution Evidence            October 2026


   Limits:  This profile produces evidence about calls that pass through
      Decision Points.  Behaviour entirely inside the model, inside a
      tool, or through a channel the Harness does not mediate is not
      recorded.

13.  Related Work

   This section states what each related document covers and how this
   profile composes with it.  The intent is to coordinate, not to
   replace.

   WIMSE AIMS [I-D.ietf-wimse-aims]:  Identity management functions and
      minimum audit fields for agents.  This profile supplies the
      evidence format AIMS leaves open;
      [I-D.thaha-wimse-agent-evidence-binding] maps the AIMS fields to
      the Execution Receipt and proposes a credential claim pointing at
      the Evidence Service.

   RATS [RFC9334] and EAT [RFC9711]:  RATS supplies roles and procedures
      for technical attestation, and EAT can convey claims about a
      measured runtime.  This profile can bind that evidence to an
      identity or operational assurance claim, but does not replace RATS
      appraisal or turn runtime integrity into a behavioural guarantee.

   Standards boundaries:  SCITT provides statement transparency, WIMSE





Thaha & Shamsudeen         Expires 1 May 2027                  [Page 54]

Internet-Draft          Agent Execution Evidence            October 2026


      provides workload identity, and RATS provides technical
      attestation and the Verifier role.  None defines a Third-Party
      Agent Assurance Assessor, a universal agent risk classification, a
      capability-audit method, or assessor qualification and
      accreditation criteria.  This profile defines the assessor role
      and carries the identifiers, commitments and results needed for
      interoperability, while leaving recognition and accreditation to
      relying-party policy, applicable external governance, and possible
      future work coordinated across the relevant communities.

   Audit architecture [I-D.kuehlewind-audit-architecture]:  Roles and
      four record types (Interaction, Action, Delegation, Authorization
      Transition).  The Execution Receipt is an Action Record at the
      Harness vantage, and the admission receipt is the corresponding
      record at the serving side; this profile is a candidate for that
      document's WI-3.  A Delegation record composes with actor_chain
      and delegation_ref.

   OAuth Token Exchange [RFC8693], Transaction Tokens
   [I-D.ietf-oauth-transaction-tokens] and Identity and Authorization
   Chaining [I-D.ietf-oauth-identity-chaining]:  Token Exchange
      expresses a chain of delegation by nested act claims; this profile
      records it as actor_chain and, unlike that specification, requires
      a Serving Party to evaluate prior actors.  Transaction Tokens
      propagate the principal of the transaction and a txn identifier
      along a Call Chain within one Trust Domain; this profile records
      txn on both sides of every call and extends the Call Chain across
      Trust Domains.  Identity and Authorization Chaining carries
      identity across Trust Domains and leaves the format of transcribed
      claims open; the Actor Chain is one concrete record of what it
      carries.  This profile complements these specifications with
      evidence and does not change them.

   Agent audit record [I-D.gilda-audit-agent-audit-record]:  A JCS-
      canonicalized in-toto Statement in a DSSE envelope, richer per
      event and oriented to authorization decisions.
      [I-D.thaha-wimse-agent-evidence-binding] defines an in-toto
      [IN-TOTO] predicate type for Execution Receipts.  An audit record
      can point to the Execution Receipt for the same call, or to the
      SCITT Receipt that registers it; the pointer associates the two
      records and dates neither of them
      ([I-D.thaha-wimse-agent-evidence-binding]).

   Agent Action Capsule [I-D.mih-scitt-agent-action-capsule]:  A JSON







Thaha & Shamsudeen         Expires 1 May 2027                  [Page 55]

Internet-Draft          Agent Execution Evidence            October 2026


      Capsule per action with disposition and an Effect Record,
      registered by Capsule ID.  Its may/did distinction is finer than
      decision plus tool_result; a Capsule ID can be the request_digest
      of a tool_call receipt.  This profile defers effect tracking to
      the Capsule.

   AI-Agent Action Receipts [I-D.noa-scitt-ai-agent-receipt]:  JCS JSON
      receipts with Ed25519 signatures, a principal class, a lifecycle
      verdict and hash chaining.  This profile shares that posture and
      adds credential, configuration and assurance statements and
      epochs.  Alignment of verdict vocabularies is desirable.

   Execution Profile [I-D.emirdag-scitt-ai-agent-execution]:  The
      AgentInteractionRecord with inputs, outputs, reasoning traces and
      redaction receipts, and the same SCITT role mapping as here.  This
      profile excludes content from statements; an AIR can be the
      retained content whose digest appears in a receipt.

   Agent Passport System [I-D.pidlisnyi-aps] and Agent Audit Trail
   [I-D.sharif-agent-audit-trail]:  A broad authority-and-evidence
      framework and a logging format respectively.  This profile could
      serve as the evidence layer of the former and commits to entries
      of the latter by digest; no dependency is created.

   EP-AEC [I-D.schrock-ep-authorization-evidence-chain]:  Composes
      heterogeneous evidence for one consequential action, and separates
      native verification, acceptance and material-action matching.
      This profile adopts its separation of correlation from matching
      for linked receipts (Section 6.7.3).  An admission or caller
      receipt that carries call_digest can be a native artifact that an
      EP-AEC evaluation composes.  The reference is informative; this
      document does not depend on EP-AEC.

   AP2 Mandates [AP2]:  User-signed credentials expressing purchase
      authorization.  A Mandate is an input to a tool_call; its digest
      belongs in request_digest, and the confirmation it embodies
      corresponds to decision confirm.

14.  Open Issues

   This section is to be removed before publication as an RFC.

   *  Delegation scope: a mechanical test that a delegated Task's, or a
      later Actor's, effective scope is no wider than its parent's needs
      a common representation of scopes (Section 6.7.1, Section 6.7.2).






Thaha & Shamsudeen         Expires 1 May 2027                  [Page 56]

Internet-Draft          Agent Execution Evidence            October 2026


   *  Supervisory Decision statement: a statement by which a Supervisory
      Authority grants, restricts, suspends, restores or withdraws
      assurance.

   *  Trust List statement: a statement by which a Supervisory Authority
      registers the assessors, schemes and foreign authorities it
      accepts.

   *  Registering RESTRICTED in the OAuth Status Types registry instead
      of using the application-specific value 0x03.

   *  A registry of record types, so that other profiles can extend
      them.

   *  A reputation statement linked through lineage_id, and whether
      identifier forms other than did:web should be allowed for
      logical_agent_id.

   *  Whether Serving Parties should also be registered by an authority.

   *  Representation mapping: a defined mapping between different
      representations of one request, including proxies that rewrite the
      path, or a statement issued by a proxy that records what it
      forwarded (Section 6.7.3). call_digest compares the request as
      sent with the request as received and cannot match a request that
      an intermediary changed.

   *  Front ends run by other operators, and shared front ends: whether
      hosts in the Serving Party's own credential is enough, or whether
      a proxy run by another operator should sign its own forwarding
      statement.  A host also does not identify one service where a
      gateway fronts several (Section 11).  Candidate designs are a path
      prefix on each hosts entry, which a Serving Party can enforce but
      a verifier cannot check because receipts do not carry the path,
      and a forwarding statement signed by the gateway naming the
      backend it routed the call to.  A third is a handoff from the
      gateway to the effect boundary, as in Section 5.8 of
      [I-D.schrock-action-evidence-boundary]: only the gateway that
      accepts the call signs, under a key the Relying Party pins,
      binding the action digest and the executor, so other
      intermediaries need not sign.  This is the question put to the
      SCITT list.

Appendix B.  Mapping to Regulatory and Standards Contexts

   This informative mapping does not claim compliance.  Execution
   Receipts, Evidence Chains and TS registration relate to Article 12
   event recording under [EUAIACT]; confirm, block and the policy per
   receipt relate to Article 14 oversight.  The open format relates to

Changes since -00

   This section is to be removed before publication as an RFC.

   *  Added call_digest (Execution Receipt key 29) and its HTTP binding,
      which covers the method, the path and query, and a digest of the
      content, and excludes scheme and authority (Section 6.7).

   *  Added hosts to the Serving Party Credential (key 7) and the Agent
      Credential (key 15), required where the chain contains an
      admission receipt that carries call_digest (Section 6.3,
      Section 6.4).

   *  egress_host is required on a tool_call or egress receipt that
      carries call_digest, and on such a receipt records the host named
      in the request, not the next network hop (Section 6.7).

   *  caller_ref may name only a receipt that carries call_digest
      (Section 6.7.3).

   *  A Serving Party computes its own call_digest, and refuses a call
      whose cd differs.  A Serving Party MUST refuse a caller reference
      it has already admitted (Section 6.7.2).

   *  Linked Verification checks that call_digest is equal on both sides
      and that the caller's egress_host is among the Serving Party's
      hosts, reported as E_CALL_MISMATCH and E_SERVING_HOST
      (Section 9.1).  The checks are renumbered.
